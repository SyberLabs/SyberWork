# Attest × SyberWork: software-factory integration study

**Date:** 2026-10-24
**Status:** Proposed design; no implementation or protocol decision is made by this study.
**Reviewed source snapshots:** SyberWork `7d6292dc0208be8d2192bf006fe135ecc01d1469` (`main`); Attest `05678342d12291ffeea70bc33de18d0278b7badc` (`main`).
**Tags:** `attest`, `syberwork`, `software-factory`, `study`.

## Decision note (ADR-style)

**Recommendation:** Keep Attest as a constrained evidence-and-repair component behind a SyberWork-owned contract and admission boundary. First integrate it through a fixed, gated worker protocol—not by importing it into `syberlabs` or treating its ledger as the case record. Kane supplies fresh browser observations; Attest classifies instruction/application disagreement and proposes a documentation-only patch; SyberWork decides whether that patch is authoritative, admitted, approved, evaluated, and promoted. Do not call a run verified until compilation is complete, exact input/output identities are bound, real Kane evidence is present, and validation passes.

This repository has architecture documents but no ADR directory or established ADR filename pattern. This decision note is therefore included here; it is not a canonical decision or authorization to implement the seam. Any protocol or authority-policy changes remain owner decisions.

## Source-grounded baseline

SyberWork already has two related but distinct histories. The `syberlabs` Build Thread journals one governed repository change: candidates are provisional, the host evaluates their exact Git tree, acceptance uses admission and a compare-and-swap branch update, and publishing is a separate effect ([Build Thread](BUILD_THREAD.md), [`syberlabs/build.py`](../syberlabs/build.py)). The `syberwork.Work` application stores version-pinned business cases and append-only hash-chained events in SQLite or PostgreSQL; its action flow records proposals, admission decisions, independent approvals, effect claims, and destination outcomes ([architecture](ARCHITECTURE.md), [`syberwork/core.py`](../syberwork/core.py), [`syberwork/storage.py`](../syberwork/storage.py)). These are not currently one shared database or one universal lifecycle. The first implementation must choose one case owner for a documentation repair and must not mirror one task into both histories.

SyberWork’s existing controls are useful but not a sandbox. Contracts are immutable by `(id, version)`; global policy can further restrict actions; verified source observations include a version; admission runs again at commit; approval binds to a proposal argument digest; and an external effect is durably claimed before I/O. Unknown outcomes remain unresolved until verified through the installed destination ([reconciliation rules](RECONCILIATION.md)). The repository explicitly says checks run in a temporary worktree with a scrubbed environment, but **that is not a sandbox** ([`syberlabs/checks.py`](../syberlabs/checks.py), [repository guidance](../AGENTS.md)).

Attest’s current `main` is the earlier “Docs That Can’t Lie” pipeline, not a completed Maintain Docs authority workflow. Its README and [architecture note at the reviewed commit](https://github.com/SyberLabs/attest/blob/05678342d12291ffeea70bc33de18d0278b7badc/docs/ARCHITECTURE.md) describe ingest → model-assisted claim compilation → shell/browser execution → deterministic verdict → render, with a doc-only repair loop. The supplied Maintain Docs implementation brief adds the target authority rules and P0 gates; no separate Maintain Docs architecture or receipt implementation was found in the reviewed Attest checkout.

Code-confirmed integration gaps at that Attest snapshot:

- [`attest/kane.py`](https://github.com/SyberLabs/attest/blob/05678342d12291ffeea70bc33de18d0278b7badc/attest/kane.py) is a `NotImplementedError` stub. [`attest/cli.py`](https://github.com/SyberLabs/attest/blob/05678342d12291ffeea70bc33de18d0278b7badc/attest/cli.py) defaults `prove` to `--runner fake`; `FakeBrowserRunner` can echo the document’s expected label. Such a result is useful for offline tests, not proof of application behavior.
- [`attest/shell.py`](https://github.com/SyberLabs/attest/blob/05678342d12291ffeea70bc33de18d0278b7badc/attest/shell.py) launches documentation shell commands with a copy of `os.environ` and a scratch working directory. A scratch directory and timeout do not restrict filesystem, network, or inherited credential access.
- [`attest/loop.py`](https://github.com/SyberLabs/attest/blob/05678342d12291ffeea70bc33de18d0278b7badc/attest/loop.py) calls the configured agent with `shell=True`. It constrains the returned diff to a single documentation file, but that diff guard does not sandbox the agent process. With `--apply`, the source is written after re-execution even when the new verdict is still not proven; this must not become an automatic promotion path.
- The loop carries the original document SHA into the patched `Doc` (`patched_doc.model_copy(..., sha256=result.doc.sha256)`). It therefore does not preserve a distinct identity for patched content. The Maintain Docs receipt must bind exact before and after bytes, and must never reuse the original content digest for the repaired content.
- Browser verdicts use a token-set similarity threshold (`label_match`, default `0.8`) in [`attest/verdict.py`](https://github.com/SyberLabs/attest/blob/05678342d12291ffeea70bc33de18d0278b7badc/attest/verdict.py). That may remain a diagnostic suggestion, but it is not a sound proof rule for exact labels, numbers, versions, permissions, or other exact predicates.
- The current `LedgerRow` records per-claim verdict summaries; it is not SyberWork’s hash-chained case history and is not a `RunReceipt`, `AuthorityDecision`, or `RepairProposal` contract. The compiler has a fallback after a second validation failure; the integration needs an explicit completeness gate rather than allowing an incomplete claim set to look like a complete run.

## Capability ownership

- **Kane — browser execution and raw evidence.** Execute an approved, bounded browser recipe against a named application revision and return the run identity, per-step result, exact stored observations, and evidence-pack artifacts. Kane is an executor/witness, not an authority source, admission engine, or promotion actor. A page observation does not supersede a protected requirement.
- **Attest — instruction/application comparison and repair proposal.** Ingest a pinned document, compile its checkable claims, request Kane observations, classify disagreement using an explicit authority policy, and produce a documentation-only `RepairProposal`. It must fail closed on ambiguity, incomplete compilation, missing evidence, stale evidence, invalid identity, or failed validation. It must not decide what is authorized, weaken a contract, execute arbitrary shell from untrusted docs, or promote a patch.
- **SyberWork — contracts, case history, authority, admission, approvals, and promotion.** Pin the repository snapshot and contract/policy versions; record evidence references; decide whether a proposed repair is admitted under the same ordered rules; require independent approval where specified; evaluate the exact candidate tree; and accept/promote only through the existing governed path. Pushing, PR creation, deployment, or other outward effects remain distinct actions.

## Proposed placement in the case lifecycle

1. **Case / snapshot.** Create one SyberWork-owned repository-change case pinned to a base commit, contract version, protected requirement source, documentation path allow-list, and target application revision. The contract must distinguish protected requirements from descriptive documentation and identify who may approve a behavior-change authority record.
2. **Admit the task.** SyberWork admits only the named documentation-maintenance operation and the fixed Attest/Kane adapter. An unknown contract, unpinned app, unapproved authority source, or path outside the documentation scope stops before execution.
3. **Observe.** Attest compiles the pinned document and the worker runs the allowed recipe. Kane executes the browser claims and returns fresh evidence for that exact app revision. The host validates receipt schema, identity, completeness, freshness, and artifact digests before recording the observation. Fake-runner output, model statements, screenshots without a correlated run, and stale evidence are not verified observations.
4. **Resolve disagreement.** Attest emits a proposed `AuthorityDecision` with the relevant contract/spec/change-decision references and evidence refs. SyberWork applies the policy: protected requirements remain binding until explicitly superseded; an approved change decision can authorize a specific description change; descriptive docs may follow approved behavior; runtime observations are evidence, not authority; missing or conflicting authority halts repair. No model-generated decision is self-authorizing.
5. **Propose repair.** A patch is a `RepairProposal` scoped to the documented paths. Register it as a provisional SyberWork Git candidate with exact base, commit, tree, changed paths, provider/revision, and diff digest. The candidate is not evidence and does not change the working tree or authoritative branch.
6. **Validate and approve.** Run whole-document compilation and the required exact predicates against the candidate, plus a fresh Kane run where the changed instructions depend on application behavior. Record failed, missing, stale, or incomplete checks as non-promotable. If policy requires approval, an independent authorized human approves the exact proposal arguments/digest; evidence cannot satisfy that approval.
7. **Execute / promote.** Only SyberWork’s normal admission and candidate-promotion rule may accept the candidate. Acceptance is a compare-and-swap to the designated non-authoritative branch. Open a PR or deploy only through separate contract actions. Never automatically apply the source patch after a failed or incomplete validation.

This placement makes Attest’s authority analysis an input to SyberWork admission, not a parallel policy engine. SyberWork’s current `Work` API has business-effect `commit`; for a repository repair, prefer the existing Build Thread candidate/check/accept path. Decide explicitly whether an outer `Work` case is necessary; if so, link it to one Build Thread and designate which journal owns lifecycle state rather than duplicating approvals or outcomes.

## Package and process boundary options

- **Add Attest as a monorepo package.** This would simplify local development and direct calls, but Attest currently has a separate Python package and dependencies (`pydantic`, `httpx`, `openai`, `rapidfuzz`, `jinja2`, `typer`, `pyyaml`). SyberWork currently keeps a small core with no runtime dependencies; importing Attest into `syberlabs` would widen that core and blur its reusable SDK boundary. Not recommended for the first slice.
- **Use Attest as a sibling dependency.** A versioned package dependency gives a clean distribution boundary and can be appropriate after the receipt/API contract stabilizes. Today the callable Kane path is a stub, the CLI defaults to fake execution, and there is no versioned receipt interface. Pinning a package now would version an unsafe/incomplete contract rather than a stable integration seam.
- **Use a gated subprocess/worker.** A SyberWork adapter can launch one pinned Attest worker with a narrow request and strict JSON receipt response, then validate the response and write evidence refs into SyberWork’s case. This is the preferred first boundary because it limits imports and makes protocol validation explicit. A process boundary alone is **not** isolation: the worker must run in a disposable least-privilege environment with no host secrets, bounded filesystem/network access, independent deadlines, and reliable process-tree cleanup. Do not invoke the current CLI as a trusted executable until fake mode is impossible to confuse with verification and P0 gates are closed.

## Data model alignment

Attest’s future names (`RunReceipt`, `AuthorityDecision`, `RepairProposal`) are design targets from the implementation brief, not current classes in the reviewed code. Keep large evidence packs outside event rows in immutable/content-addressed storage; put compact digest-bound references in the SyberWork history. Record both raw byte SHA-256 and Attest’s normalized-text digest when CRLF/BOM normalization matters, plus repo commit, app revision, compiler/runner versions, policy/contract version, and run id.

- **`RunReceipt` → receipt-reference observation and candidate evaluation evidence.** Record a compact receipt reference in an existing `observed` value: document input digest, compiled-claim-set digest/completeness, application revision, Kane run id, evidence-pack digest, exact per-claim predicate results, and the distinct post-repair digest if one exists. The bridge starts unverified; only a destination check may support a later verified observation. `candidate_evaluated` should name the exact candidate commit/tree and required validation checks. A check output digest alone is not the full receipt; retain the receipt artifact and verify its digest on read.
- **`AuthorityDecision` → proposed interpretation plus SyberWork admission.** Store its policy/source references and result as a compact observation/provenance artifact. The canonical `decision` event remains SyberWork’s ordered-rule result for a proposal under the case contract and active global policy. Do not allow an Attest verdict to write or override `allowed`, `needs_approval`, or `denied`.
- **`RepairProposal` → provisional Git candidate and ordinary approval.** Store the exact diff digest and changed paths, and bind the approval to the resulting SyberWork proposal/candidate identity and argument digest. Treat the proposer’s text, rationale, and patch as untrusted signals. Promotion uses existing candidate evaluation and human-role rules.

The `sdk.syberlabs.space/v0alpha1` event schema enumerates existing event kinds and the observation shape is closed except for its JSON `value`; candidate and evaluation records already bind commit/tree and changed paths. The MVP should not add event kinds or silently change frozen bodies. Prefer existing `observed`, `candidate_registered`, `candidate_evaluated`, `proposed`, `decision`, `approved`, and effect events with validated artifact references. If these cannot express the receipt without weakening semantics, take a separately reviewed protocol change rather than overloading a field.

## Kane Factory receipt-to-reconcile loop (priority addendum)

The MVP handoff is **Attest authority gate → `.attest/receipts/<case>.json` (`attest.receipt/v0`) → SyberWork observation bridge (`verified: false`) → destination-verified reconcile**. This is a proposed adapter contract, not a claim that Attest or the bridge already implements it.

1. **Authority gate first.** Attest evaluates the pinned protected requirements and approved change record. Ambiguous or missing authority stops before repair; a receipt records the authority references and outcome, but never grants SyberWork admission or approval.
2. **Receipt artifact.** Write one case-scoped JSON receipt with protocol `attest.receipt/v0`, case/contract/policy and repository/application identities, exact input and proposed-output digests, compilation completeness, authority references, Kane run/evidence-pack digests, per-claim results, and proposal identity. The case path component must be a host-issued safe ID; the filename is not a trust boundary. SyberWork validates schema, case binding, and artifact digest on ingestion.
3. **Unverified bridge.** Append an ordinary SyberWork `observed` event that references the receipt artifact and digest with `source: "attest"`, `version: "attest.receipt/v0"`, and `verified: false`. Do not mutate this hash-chained event or use it to satisfy contract facts, approvals, or promotion gates. A local digest check alone does not verify a destination outcome.
4. **Destination check and reconcile.** For an external effect, use a SyberWork action with an authoritative destination lookup. Reconcile only when the destination confirms the original idempotency key, exact request digest, committed state, and external record ID; pending, missing, or mismatched status remains unresolved. Append the normal `reconciled` proof, then (if a contract needs a verified observation) append a separate observation linking that proof and the receipt with `verified: true`. A candidate check or local branch compare-and-swap is not itself a destination reconciliation; do not synthesize a `reconciled` event for either.
5. **Continue ordinary governance.** Candidate evaluation, independent approval, and promotion remain separate SyberWork gates. Destination reconciliation proves the configured effect outcome, not that Attest's authority judgment was correct or that Kane evidence is complete; those checks stay independently bound in the receipt and candidate evaluation.

If the chosen destination has no authoritative status lookup, keep the outcome unverified and unresolved rather than treating an Attest receipt, Kane observation, screenshot, or caller-supplied success field as reconciliation. Selecting or building that destination adapter is an explicit next experiment, not an implicit receipt behavior.

## Security: P0 gates against SyberWork trust boundaries

The main risk is treating Attest’s scratch directory or SyberWork’s temporary worktree as confinement. Both repositories currently execute subprocesses in the host process context; SyberWork explicitly documents that its runner is not a sandbox, and Attest’s shell runner inherits the environment. A malicious or simply unsafe documentation command could read credentials, mutate files outside scope, access the network, spawn persistent processes, or alter the application being “verified.” A doc-only patch guard limits diff paths, not process authority.

Before any integration may issue a successful receipt or promote a patch, require all of these:

- Run commands only from a contract-owned allow-list of recipes, not arbitrary fenced commands supplied by a document or model. Execute them in a disposable, low-privilege worker with an explicit filesystem and network policy; provide no SyberWork database credentials, GitHub token, model key, user browser profile, or write-capable host mount.
- Use an isolated browser profile and explicitly bound target origin/app revision; capture Kane’s raw pack and bind its digest/run id to the observation. Reject fake/simulated runner modes as evidence, not merely label them differently in the UI.
- Use separate bounded deadlines for compilation, shell/recipe execution, Kane, and repair; terminate the process tree and clean up in `finally` on every exit path. Never kill an unrelated process by port ownership.
- Require complete compilation, no unresolved required claims, exact before/after identities, exact comparisons for exact predicates, path containment for evidence/artifact access, and fresh evidence on the candidate’s exact application state. Failed or incomplete validation cannot source-apply or promote.
- Keep artifacts immutable and content-addressed, enforce retention/access controls, and treat the SyberWork hash chain as integrity evidence within its database trust boundary—not protection from a database operator who can rewrite the chain.

The uploaded implementation brief calls out these items as Stage 0, including simulation/verification separation, incomplete compilation, failed-validation auto-apply, stale content digests, fuzzy exact predicates, bare-URL rendering/evidence-path containment, process deadlines/cleanup, and disposable execution. They are integration blockers, not optional hardening.

## Smallest vertical slice to a software factory

After P0 isolation and receipt gates are closed, use one synthetic local web application, one protected behavior requirement, one descriptive quickstart, and one deliberate approved behavior change. Keep the application fixed at a known commit and use real Kane evidence—never a FakeBrowserRunner receipt. The SyberWork contract has a single mutable docs path, immutable protected source, bounded recipes/checks, required fresh Kane validation, and an independent approval role for promotion.

The slice should demonstrate exactly three paths:

1. **No disagreement:** Attest compiles completely; Kane’s exact observed label satisfies the contract predicate; no repair candidate is created.
2. **Authorized documentation repair:** a versioned approved change record permits the documentation to describe the new behavior; Attest emits a doc-only proposal with different before/after byte digests; fresh Kane evidence and whole-document checks pass on that candidate; an independent approver authorizes the exact candidate; SyberWork accepts it to the non-authoritative branch.
3. **Refusal:** an unapproved proposal that weakens a protected requirement (for example, changing a required condition into an optional one) is denied, remains a recorded provisional attempt, and cannot be source-applied or promoted.

This single slice proves the boundary and receipt semantics, not general documentation correctness, a universal browser oracle, customer adoption, or production safety.

## Non-goals and kill criteria

**Non-goals:** a second Attest/Kane assurance graph; arbitrary model shell access; automatic weakening or rewriting of protected requirements; replacing SyberWork contracts/admission/approval; broad autonomous code repair; Reconcile Spec beyond diagnosis/handoff; automatic merges, deployments, or customer-side actions; and any claim that “green” means universally true.

**Kill or pause the integration if:** a run can look verified with fake, missing, stale, wrong-version, or incomplete evidence; exact content or application identity cannot be bound end-to-end; authority ambiguity is converted into an automatic repair; failed validation can still apply/promote; an untrusted recipe can escape its isolation or access host secrets/writes; evidence artifacts are mutable or cannot be retrieved by verified digest; or the only way to fit the feature requires changing frozen event semantics without a separate owner-approved protocol decision.

## Open questions and next experiments

1. Which SyberWork history owns the complete repository-repair case: the Build Thread journal, `syberwork.Work`’s application database, or a deliberately linked pair? Recommend one authoritative lifecycle journal before implementation.
2. What is the contract’s canonical source of protected requirements and approved behavior changes, who can issue each, and how is a supersession scoped to exact documentation claims?
3. Which Kane CLI/evidence-pack version and result fields are stable enough to bind into a receipt? Can one run be correlated to exact target revision and exact per-step observations without a signed-in user profile?
4. Where will immutable receipts, screenshots, and packs live, with what size limits, retention, privacy, and corruption handling? The reviewed SyberWork stores do not expose a general evidence-blob store.
5. What isolation worker is available for arbitrary documentation recipes, if any? If none, can the MVP avoid executing document-supplied shell and instead use only fixed contract recipes plus browser evidence?
6. Prototype three authority cases (no drift, authorized descriptive change, unauthorized weakening) against a minimal contract and verify the resulting decisions from the journal alone.
7. Add adversarial worker tests for secret/environment leakage, path traversal, artifact substitution, timeout cleanup, incomplete compilation, exact numeric/label mismatches, fake-runner rejection, and failed-validation non-application before accepting the first verified receipt.

**Planning estimate (not measured):** approximately **8–12 engineer-days** for one engineer to deliver the first end-to-end, fail-closed vertical slice, assuming an available disposable worker and a stable Kane CLI interface. This excludes building a new isolation service; if no suitable worker exists, estimate that separately after selecting its threat model and deployment target.
