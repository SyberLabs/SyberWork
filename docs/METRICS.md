# Metrics: per-work-item numbers from the journal

```bash
syberlabs metrics                         # one row per thread in this home's journal
syberlabs metrics --json                  # every number with the event hashes it came from, and a summary
syberlabs metrics --csv --since 2026-10-20
syberlabs metrics --check                 # exit 1 when a delivered item has an unknown metric (for CI)
syberlabs metrics --from-export receipts/*.json   # records written by `syberlabs export`; no repository needed
syberlabs settle                          # record merges, closes and reviews of opened pull requests (section 3)
```

The service serves the same fold at `GET /metrics/work_items` and `GET /metrics/work_items/<thread>` (bearer token, read only, beside `GET /metrics/<key>`), and the operator page (`python -m syberlabs.dashboard`) has a **Work items** section with the nine columns.

## The rule

Every number is computed from the journal, never counted alongside it. `syberlabs.metrics.work_items(events)` is a pure function of a thread's events: two readers of the same record get the same numbers, and each number carries a `basis`, the hashes of the events it came from (`provenance(item, metric)` lists them with their sequence numbers and kinds), so a certificate can cite them. Anything the journal did not carry becomes a journal record first (section 3) and a metric second. Reading writes nothing.

A **work item** is one Build Thread: from `case_created` to the merge of the pull request its `github_pull_request` effect opened, or to `case_cancelled`. An item that never publishes counts as started and not delivered.

**`unknown` is a value.** When the fact a metric needs is not in the record, the metric is `unknown` (`"unknown"` in JSON and CSV, `value: None` in Python), never 0. Zero means the record shows none; unknown means the record cannot say. `summary` computes means and medians over known values and counts the unknowns beside them.

## 2. The nine metrics

| Metric | Derivation from the journal | Unknown when |
|---|---|---|
| **cost** ($) | Per search, `search_finished.spend.dollars`; for a search with no `search_finished`, the `candidate_registered.spend.dollars` of its registrations. Refusal spend (`proposal_refused.value.spend`) is pending usage the next registration or the search total already carries, so it is not added again. Labelled `cost_basis`: `host_observed` when a call crossed the host's meter, `declared` when a provider only declared `model_usage`, `none` when nothing was recorded. Beside it, `lane` is the registrations' declared credential lane (`signal.lane`: `api`, `subscription_local`, `seat_team_enterprise`, `provider_3p`; `mixed` when they differ), shown in the table as `(host_observed, api)`. | basis `declared` or `none`, a model the contract does not price, or a lane whose `signal.cost_basis` is `none` (no per-call bill; the note says so) |
| **turns** (calls) | Records carrying declared `model_usage`: registrations and `proposal_refused` observations (adjacent records with identical usage are one call: the items after a repair call's first are refused `limit` with that call's usage), plus `critic_usage` facts. A registration whose signal declares `harness_turns` (a harness run: Claude Code's `num_turns`, each turn a model request) counts as that many. Migrations are not calls. | any registration carries no usage (its calls happened outside the host, for example `--from-worktree`) |
| **agent_time** (hours) | `pr_merged.merged_at` minus `case_created.at`. Human review time is inside the interval by construction. | no `pr_merged` fact |
| **fix_rounds** | Registrations that follow a failed evaluation (a required check of the contract not `passed`; every recorded check when the contract is not supplied), each failed evaluation counted once. First attempt right is `fix_rounds == 0` with the first candidate accepted. | never |
| **web_lookups** | Sum of `signal.tool_usage.web_search + web_fetch` over registrations. | any registration did not declare either |
| **githits_lookups** | When the record holds `lookup` facts made from GitHits client records (tool `githits.<op>`: the `--githits` route, `docs/CLAUDE_CODE.md`), their number plus host-observed GitHits MCP attempts: one per authentic record or MCP attempt, calls whose answer was refused included. Synthetic `githits.unrecorded` facts are never authentic records and always make the count unknown. A `githits.doctor` fact (the operator's readiness check, `docs/GITHITS.md`) is never counted, and when the client-record facts are all doctor facts the count is 0, not the declared sum. Otherwise the sum of `signal.tool_usage.githits` over registrations. | no client-record fact, and any registration did not declare it; or a call's `signal.githits.mismatch` says a launcher call the guard passed left no client record, or a client-record fact is `unguarded` (a record no guarded launcher call stands behind, a failed call's record, or a `githits.unrecorded` fact standing for a failed call's launcher call that left none): the record cannot say whether those reached GitHits |
| **delivered** | `true` with a `pr_merged` fact (for the opened pull request's number); `false` when no pull request was opened, the thread was cancelled, or a `pr_closed` fact (same number) says it was closed unmerged. `opened` is a separate column: a `github_pull_request` effect that succeeded, or a verified reconciliation of one. | a pull request is open and neither `pr_merged` nor `pr_closed` is in the record |
| **review_rejections** | Critic checks (`critic`, `critic.*`) that did not pass, or that passed with a host critic observation counting a high finding (what `critic.no_high_finding` refuses); plus `review` facts with verdict `fail` and `pr_review` facts with state `changes_requested`. | never |
| **human_interventions** | `human_intervention` facts, plus `proposed`, `approved` and `case_cancelled` events whose actor is neither `syberlabs.host` nor the thread's unattended runner (`unattended.by`) and whose proposal no fact names. | never |

Both lookup counts are attempted lookups: a lookup the query guard blocked is still counted (`docs/CLAUDE_CODE.md`, the query guard). On the `--githits` route a lookup is a call the client made and recorded (a call it refused itself, `excluded_target`, included); a shell command the guard blocked (a `Bash` call, or a `PowerShell` call under `--allow-code-tools-with-mcp`) never reached the client, so it is not in `githits_lookups`, and its `lookup` fact (tool `Bash` or `PowerShell`, its rule) is counted in `lookups_blocked`. Beside the nine, every work item carries **`lookups_blocked`** (in `to_dict`, `--json` and `provenance`; not a table column or a CSV field): the host's `lookup` facts whose `guard` names a rule (not `pass`, and not `unguarded`, which means the hook never decided). It is `unknown` when a `lookup` fact carries no `guard` (recorded before the guard existed) or when lookups were counted but no `lookup` fact is in the record (an adapter that only declared counts), and 0 with no lookups at all.

`summary` reports `items`, `opened`, `cancelled`, `delivered` (`yes`, `no`, `unknown`), `delivered_rate` (only when no item's delivery is unknown; otherwise `delivered_rate_bounds` gives the range), `opened_rate`, the count per `cost_basis`, and per metric `known`, `unknown`, `total`, `mean`, `median`.

## 3. The facts, and who writes them

All are `observed` events written by the host (`actor: syberlabs.host`, `verified: true`) through `Session.observe`, the route `unattended`, `base_evaluation` and `proposal_refused` use. No event kind is added; `spec/event.schema.json` and the golden traces are unchanged.

- **`tool_usage`** on the candidate's `signal`. The adapter protocol's response may carry `tool_usage: {web_search, web_fetch, githits, other: {name: n}}` beside `usage`. `CommandProvider`, `RepairProvider` and `CommandMutator` (via the evolutionary provider's signal) copy it through `providers.tool_usage`: integer counts only, at most 16 `other` names of at most 64 characters. An item's own `signal.tool_usage` is dropped; only the call's declaration reaches the record, and an adapter that declares nothing leaves it absent. `adapters/anthropic_adapter.py` passes through the SDK's `usage.server_tool_use` (`web_search_requests`, `web_fetch_requests`) when the SDK reports it; it reports no GitHits count, so `githits_lookups` stays unknown for that adapter.
- **`lane`** and **`cost_basis`** on the candidate's `signal`, written by `ClaudeCodeProvider` (`docs/CLAUDE_CODE.md`): `lane` in `api | subscription_local | seat_team_enterprise | provider_3p`, `cost_basis` in `billed | estimated | none` (the credential lane's bill, not the suite's `host_observed | declared | none`), with `estimated_usd` (Claude Code's own `total_cost_usd`, an estimate, never spend), `harness_turns`, and `tool_usage` counted by the host from Claude Code's stream.
- **`lookup`**, value `{tool, query_digest, query_chars, at, ok, guard}`, one per GitHits or web tool call a Claude Code run made, versioned `<search>.<call>.<n>`, written by the host from the stream before the call's candidate, through `GitSearchSpace.observe`. The query text is never stored: `query_digest` is its SHA-256. `guard` is the query guard's decision: `pass`, a rule name (`ok` is then false), or `unguarded`. The suite counts lookups from `signal.tool_usage` and `lookups_blocked` from these records; they also let a reader date lookups and match repeated queries. On the `--githits` route the host writes two more forms after the call, from what it observed itself: one per authentic GitHits client record, tool `githits.<op>`, value `{tool, query_digest, request_id, status, at, results_returned, results_dropped, results_dropped_license, latency_ms, contamination_blocked, ok, guard}` (`query_digest` is the client's digest of the request it sent, `request_id` GitHits' `X-Request-ID`), from which `githits_lookups` is counted (`githits.doctor` excepted); and one per `Bash` or `PowerShell` call the guard did not pass, tool `Bash` or `PowerShell`, value `{tool, query_digest, query_chars, at, ok, guard}`.
- **`human_intervention`**, value `{kind, by, at, note}` and `proposal` for an act on one; `kind` is `message`, `commit`, `approve`, `edit` or `override`. Written by `syberlabs note --intervention KIND [--note TEXT]`, and automatically by `syberlabs accept` (`approve`), `syberlabs approve` (`approve`) and `syberlabs check --rerun` (`override`) when the acting actor is a person: not `syberlabs.host` and not the thread's unattended runner. `syberlabs run` writes none. A note is at most 500 printable characters; one that looks like a credential is refused.
- **`review`**, value `{verdict, reviewer, revision, findings_high, comment_url, by, at}`, versioned by the revision. Written by `syberlabs review --record --verdict pass|fail --reviewer NAME --revision R [--findings-high N] [--url URL]`; `syberlabs review` lists them.
- **`critic_usage`**, value `{candidate, check, usage}`. A findings document may declare `usage` (`spec/finding.schema.json`); the check record's fields are frozen (`spec/candidate.schema.json`, `evolution.evaluation_record`), so the host writes it as a second observation beside the critic's, same source `check:<name>` and version (the output digest).
- **`pr_merged`** `{number, merged_at, merge_commit, merged_by}` (version: the merge commit), **`pr_closed`** `{number, closed_at}` (version: `closed_at`) and **`pr_review`** `{number, review_id, state, reviewer, at}` (version: the review id), source `github:<owner/name>`. Written by the settlement poll `syberlabs.settle`: `syberlabs settle [--thread ID]` runs one pass, and `syberlabs run` runs one at the end of each pass when an installed `github_pull_request` action's `token_env` is set. A pass reads `GET /repos/{repository}/pulls/{number}` and `/reviews` (standard library `urllib`, 30-second timeout, the action's `api`, `repository` and token) for every pull request a thread's `github_pull_request` effect opened (`external_id` is the number). `pr_merged` is written once, when GitHub says the pull request was merged, and the pull request is not polled after that; `pr_closed` once per closing without a merge; `pr_review` once per review id, for submitted reviews only (pending ones are not GitHub's record yet), `state` lowercased (`approved`, `changes_requested`, `commented`, `dismissed`) and `at` GitHub's `submitted_at`. Reviews are recorded before the merge in the same pass. GitHub's answer is checked before anything is written: the number asked for, the thread's branch as head, logins, a 40-hex merge commit, ISO 8601 times; a non-200 answer, a network failure, a mismatch or a missing token records nothing for that pull request and is reported on stderr, so an unknown stays unknown. The token is never written to the journal or printed.

## 4. Accuracy, stated honestly

- **Cost** is exact for host-metered API lanes and unknown for others; the label says which. Critic usage is declared by the critic, so it counts as a turn and is left out of host-observed dollars.
- **Turns** count host-recorded calls with declared usage. A harness's internal loop is one call unless the registration declares `harness_turns`; a harness call refused `no_change` carries no `harness_turns` and counts as one. A stand-in adapter that reports identical usage on two consecutive calls with nothing recorded between them would be read as one call.
- **Agent time** includes human review time; `human_intervention` facts let a reader split it, and the `unattended` flag marks items where no person was asked. It is known from the first settlement pass after the merge; `merged_at` is GitHub's clock and `case_created` the host's, so skew between them is inside the number.
- **Lookups** are adapter-declared for JSON adapters. For `ClaudeCodeProvider` the host counts them from Claude Code's stream and writes one `lookup` record per call; the stream is still Claude Code's report of what it did, not a network observation, and lookups by a call whose answer was refused are not counted (`spec/GAPS.md` 52, 54). On the `--githits` route GitHits lookups are counted from the host's own client's records instead: each is a request the host's code sent (or refused itself) and signed under a per-call key, counted even when the call's answer was refused; a thread that mixes this route with GitHits MCP lookups counts only the client's (`spec/GAPS.md` 59).
- **GitHits lookups against the server** (`tests/test_githits_accounting.py`, 2026-10-26, with #135 and #142). An independent counter, the loopback GitHits' own log of the requests it received, was compared per work item with the journal's `githits.<op>` facts and `githits_lookups`, through the real provider, launcher and client. They agree, request id for request id and digest for digest, for: a lookup; results dropped for an excluded owner or the license; launcher commands the guard blocked (nothing reaches the client or GitHits); 401, 404, 500, 503 and 429 answers (one request each: the client does not retry); a timeout and a dropped connection (the fact has no request id: the client never read one); an answer the client cannot read (recorded as `malformed_response` since #142); five lookups in one call, in order, the example sent with `license_mode: strict`; eight launcher processes at once; fix rounds, up to the first acceptance as `experiment` reads it; and arm A, which has no launcher and no GitHits variable and counts a known 0. Two kinds of lookup are counted though GitHits never received them, by this metric's definition: a target the client refused (`excluded_target`) and a connection that never opened. Since #142 each record says whether its request was written (`sent`: true, false, or null when interrupted in flight), and in every case above the facts with `sent: true` are exactly the requests GitHits received. The count is `unknown` where the journal cannot say how many requests left (above): a command the launcher's entry refuses (`doctor`, `--help`, `--license-mode`) or a usage error sends nothing and leaves no record, but the guard passed it, and a launcher killed outright (SIGKILL) or a record that cannot be written leaves the same journal after its request left; and a lookup in flight when the Claude Code call times out, whose failed call journals its records `unguarded`, or a `githits.unrecorded` fact when it has none (#142). It is still a known number, possibly one short, when an unrecorded launcher call is in a call refused `no_change`, because that mismatch rides only on a registered candidate's signal (`spec/GAPS.md` 59 (12)).
- **Interventions** undercount messages to an agent made outside the CLI, and cannot tell an agent from a person when both act under one identity: on a thread without an unattended runner, every `proposed` by a non-host actor is a person's act.
- **Delivered** is `unknown`, not `false`, for an opened pull request until a settlement pass has seen it merged or closed. `--check` judges the items the record shows as delivered, so once a merge is recorded an item whose cost, turns or lookups are unknown (every `--from-worktree` proposal) fails it. A pull request closed and then reopened keeps its `pr_closed` fact and reads `false` until a merge is recorded (`spec/GAPS.md` 53).
