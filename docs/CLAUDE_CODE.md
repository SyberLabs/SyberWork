# Claude Code as a proposer

```bash
syberlabs propose --claude-code --trusted-tree                    # your own Claude Code login (subscription_local)
syberlabs propose --claude-code --bare                            # ANTHROPIC_API_KEY in your environment (api)
syberlabs propose --claude-code --bare --max-calls 1              # one shot instead of the repair loop
syberlabs propose --claude-code --bare --mcp-config githits.json --allowed-tools Read,Edit,Write,Glob,Grep,mcp__githits
syberlabs propose --claude-code --bare --guard-max-lines 3 --guard-max-chars 400   # the query guard's thresholds (defaults)
syberlabs propose --claude-code --bare --githits                  # GitHits through the API client (arm B of the pilot)
```

`syberlabs.claude_code.ClaudeCodeProvider` is the repair loop (`providers.RepairProvider`, the factory's default proposer path) with one call replaced. Each call:

1. checks out the parent, the thread's base on the first call and the failed candidate on a repair, in a detached temporary worktree (`gitspace.Repo.worktree`; the developer's working tree is never touched);
2. builds the prompt with `adapters/anthropic_adapter.py: build_prompt` for the same request the JSON adapters get (objective, scope, and on a repair the failed checks' output and the failed candidate's files), and writes it to Claude Code's standard input;
3. runs `claude -p` in that worktree under the operator's own credential;
4. reads the change back from the worktree with git: every path that differs from the parent, committed or not, tracked or untracked and not ignored, with its text. The model's prose is never read as a change;
5. hands that change to the host, which registers, scopes and evaluates it like any candidate. While it fails, the next call repairs it, until one passes, `--max-calls` is reached or the budget stops it.

Nothing here makes a provider's claim into evidence: only the host's own checks on the candidate's tree decide.

## The command it runs

Read from the installed `claude --help` (Claude Code **2.1.309**, the VS Code extension's native binary, 2026-10-23) and Anthropic's CLI reference and headless pages (`code.claude.com/docs/en/cli-reference`, `code.claude.com/docs/en/headless`, read the same day):

```
claude -p [--bare] --output-format stream-json --verbose --permission-mode dontAsk --restricted
       --tools Read,Edit,Write,Glob,Grep --allowedTools Read,Edit,Write,Glob,Grep --setting-sources user --strict-mcp-config
       --no-session-persistence --append-system-prompt "<harness note>" --settings <guard settings file>
       [--max-turns N] [--mcp-config FILE]
```

| Flag | Why |
|---|---|
| `-p`, prompt on stdin | Non-interactive. The prompt goes on standard input (capped at 10 MB by Claude Code), not in argv: no Windows command-line limit and no prompt in a process listing. |
| `--output-format stream-json --verbose` | The only format that carries every turn: each assistant message with its `usage` and `model`, every `tool_use` and `server_tool_use` block, every tool result, the `system/init` event and the final `result` (`num_turns`, `total_cost_usd`, `subtype`). `json` gives the totals but not the tool calls. |
| `--permission-mode dontAsk` | Denies every call that would otherwise prompt; nobody is there to answer. The permissions page (`code.claude.com/docs/en/permissions`, read 2026-10-23): dontAsk "auto-denies every call that would otherwise prompt"; "File reads in your working directories ... still run", and file reads need no approval only "within the working directory and additional directories". |
| `--restricted` | Confinement for the query guard's files (below). 2.1.309's `--help`: "removes the built-in tools that run commands or code (Bash, PowerShell and the other code-running tools) and WebFetch unless --tools names them, and ignores user, project and local settings files (managed settings and --settings still apply ...). Also confines the file tools to the working directories (--add-dir included), refuses bypassPermissions, and lets only a person or the configured permission handler approve writes to settings, git and tool-configuration files." The CLI reference (`code.claude.com/docs/en/cli-reference`, read 2026-10-23) says the same and "Requires Claude Code v2.1.248 or later", below the provider's 2.1.295 floor. |
| `--tools LIST` | The built-in names among the allowed tools (`claude_code.built_in_tools`: MCP tools left out, since `--tools` "doesn't affect MCP tools", and a rule's specifier dropped, so `Bash(git log *)` is `Bash`). Under `--restricted` a code-running tool or `WebFetch` exists only when named here, so it exists only when the operator allows it by name. |
| `--allowedTools LIST` | The explicit tool list (`--allowed-tools` on our CLI; default `Read,Edit,Write,Glob,Grep`: no shell, no web). |
| `--setting-sources user` | Loads no project or local settings from the tree, which a previous call's model may have written. Under `--restricted` user settings are not loaded either (only managed settings and `--settings`); the flag stays for a Claude Code that ignores `--restricted`. |
| `--strict-mcp-config` | Only servers named with `--mcp-config` connect; the tree's `.mcp.json` never does. Always passed, so the off arm of an A/B run has no MCP server at all. |
| `--no-session-persistence` | Per-candidate runs in temporary worktrees are not saved as resumable sessions. |
| `--append-system-prompt` | One fixed harness note: edit files in the current directory, the host reads the change with git, do not commit. The task prompt itself is the adapter's. |
| `--settings FILE` | The query guard (below): a temporary settings document the host writes per call, in its own directory outside the worktree, holding one `PreToolUse` hook and nothing else. `--settings` sits above user, project and local settings and below managed settings (`code.claude.com/docs/en/settings`, read 2026-10-23); `--setting-sources` names only `user`, `project` and `local`, so it does not filter it. |
| `--max-turns N` | Optional cap on agentic turns (listed in the CLI reference; not in 2.1.309's `--help` text). A run that reaches it still yields whatever it changed. |
| `--bare` | The API-key lane: skips hooks, plugins, MCP auto-discovery, auto memory and `CLAUDE.md`, and never reads a subscription login or the keychain. |
| `--mcp-config FILE` | One more MCP server, for example GitHits. |

With `--githits` (below) three items differ and nothing else: `--tools` gains `Bash`, `--allowedTools` gains
`Bash(<launcher>:*)`, and the `--append-system-prompt` text gains the adapted GitHits skill after the harness note.

The executable is `claude` on `PATH`, or `SYBERLABS_CLAUDE_BIN` (a path, or a command line; the tests use it to run a stand-in). It is the operator's own, unmodified binary; SyberLabs never ships, patches or downloads one. When the provider is built it runs `claude --version` and refuses (`invalid_provider`) a version it cannot read or one below 2.1.295. It reads only the documented form: the whole output, stripped, must be `X.Y.Z (Claude Code)` (`claude_code.version_tuple`), so a banner or any other line before or after it is refused rather than searched for a number. The floor is 2.1.295 (`claude_code.MIN_VERSION`), the release the hooks reference gives for `onFailure: "block"`: an older Claude Code ignores that field and lets a lookup through when the hook crashes or times out. The version read is recorded on every candidate as `signal.harness.installed_version`.

## Credential lanes: bring your own credential

Anthropic's Claude Code legal and compliance page (`code.claude.com/docs/en/legal-and-compliance`, read 2026-10-20; see the officer report `2026-10-20-syberfactory-claude-native-operability.md`) allows an end user to sign in to the unmodified Claude Code with their own subscription, and a customer to give its own users API keys; it does not allow a third party to collect, store or intermediate claude.ai credentials or to route requests through someone's plan on behalf of others. So **SyberLabs never stores, pools or forwards a credential.** The operator's own Claude Code runs under the operator's own login, or with `--bare` and the operator's own API key. The provider holds no credential and writes none to the record; it records which lane ran.

Every candidate this provider registers carries `signal.lane` and `signal.cost_basis`:

| Lane | When | `cost_basis` | Cost in the record |
|---|---|---|---|
| `api` | `--bare` (default there) | `billed` | Tokens × the contract's `budget.prices`, through the host's meter, so the dollar budget applies |
| `provider_3p` | `--bare --lane provider_3p` (Bedrock, Vertex or Foundry credentials) | `estimated` | Priced the same way; the bill is the cloud provider's |
| `subscription_local` | No `--bare` (default there): an inherited login | `none` | Not priced: there is no per-call bill; the dollar budget does not apply |
| `seat_team_enterprise` | `--lane seat_team_enterprise` | `none` | As above |

Claude Code's own `total_cost_usd` is recorded as `signal.estimated_usd`. It is a client-side estimate and is never used as billed spend. On a lane without a per-call bill, `syberlabs metrics` keeps cost `unknown` and says why; turns, lookups and the other metrics are still counted. `--bare` with `subscription_local` or `seat_team_enterprise` is refused (bare mode never reads a login). On those two lanes the provider removes from Claude Code's environment every variable in `claude_code.LOGIN_LANE_DROPPED_ENV`: each one Claude Code's environment reference (`code.claude.com/docs/en/env-vars`, read 2026-10-23) documents as an Anthropic credential or endpoint other than the login (`ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `ANTHROPIC_BASE_URL`, `ANTHROPIC_CUSTOM_HEADERS`, workload-identity and mTLS settings) or as a third-party switch, endpoint, project, region or credential (`CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, `CLAUDE_CODE_USE_MANTLE`, `CLAUDE_CODE_USE_ANTHROPIC_AWS`, `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`, `CLAUDE_CODE_SKIP_*_AUTH`, `ANTHROPIC_BEDROCK_*`, `ANTHROPIC_VERTEX_*`, `ANTHROPIC_FOUNDRY_*`, `ANTHROPIC_AWS_*`, `CLOUD_ML_REGION`, `VERTEX_REGION_*`), and the cloud SDKs' `AWS_*`, `GOOGLE_*`, `GCLOUD_*` and `AZURE_*`; `CLAUDE_CONFIG_DIR` (the page: "Override the configuration directory ... All settings, session history, and plugins are stored under this path", so it can point at another login or `apiKeyHelper`); and the proxy variables `HTTP_PROXY`, `HTTPS_PROXY` and `NO_PROXY` (on the page) and `ALL_PROXY` (not on the page; common HTTP clients read it), each also in lower case, which do not bill but change where requests and lookups go. `CLAUDE_CODE_OAUTH_TOKEN` stays: it is the login. So a run labelled subscription cannot be billed by a key or routed to a billed provider. On `--bare`, a set `ANTHROPIC_BASE_URL` or third-party switch (`claude_code.THIRD_PARTY_SWITCHES`; `0`, `false`, `no` and `off` count as unset) means the run does not go to Anthropic's API under the operator's key: the lane must be `provider_3p`, and `api` is refused when the provider is built (`invalid_provider`) and again at each call (`provider_lane_mismatch`) in case the environment changed. The provider never passes `SYBERLABS_CERTIFICATE_SEED` on any lane. Otherwise Claude Code inherits the caller's environment, as every provider command does.

## Trust

Without `--bare`, `claude -p` runs the hooks in the tree's `.claude/settings.json`, connects the servers in its `.mcp.json` and reads its memory files (`CLAUDE.md`, `CLAUDE.local.md`) as instructions, with no workspace trust dialog and no per-server prompt (headless page, above). The provider therefore **refuses to run non-bare unless the operator passes `--trusted-tree`**, and the refusal (`untrusted_tree`) says why. Trusting the tree means trusting the repository and every tree the model writes in it, because a repair call runs in the failed candidate's tree. Two flags narrow that in every mode: `--setting-sources user` (no project or local settings, so no project hooks) and `--strict-mcp-config` (no `.mcp.json` servers). Memory files are still read from the working directory in non-bare mode, and a repair call runs in the failed candidate's tree, so a model could write the next call's instructions. Before each repair call the provider therefore compares the parent candidate's changed paths against the thread's base, and refuses the call when any is an instruction file: `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md` or `.mcp.json` at any depth, a path named `.claude` itself (a file, or a symbolic link standing in for the directory) or anything under a `.claude/` directory (settings, rules, skills, agents, commands), compared case-insensitively, or a symbolic link (git mode `120000`) whose target, resolved against the link's directory, is one of those or lies under a `.claude` directory (`claude_code.instruction_link`). Not caught: an `@path` import in an unchanged `CLAUDE.md` that names a file the model edited (the import's target is an ordinary path; the memory file that imports it did not change), and a link to a directory that merely contains a `CLAUDE.md`. The refusal is journaled as `proposal_refused` with reason `instruction_files_changed` and the search ends with that error; no call is made on that parent. The base's own files are the operator's and are allowed, so the first call is never refused. The check runs in bare mode too (bare mode skips memory discovery, but skills still resolve), which means an objective that edits these files gets one shot, not a repair loop. `--bare` needs no declaration. None of this is a sandbox: Claude Code runs with the operator's permissions, like every provider command.

**Pilot condition.** This repository's own tracked `CLAUDE.md` describes the GitHits runtime. A pilot run on a SyberWork worktree reads it in both arms of the A/B (non-bare), which is equal across arms but is part of what the model was told; record it with the pilot's conditions.

**Timeouts.** Claude Code runs in its own session (POSIX) or process group (Windows, `CREATE_NEW_PROCESS_GROUP`); when it exceeds its time or output limit the provider ends the whole group or process tree with `checks._stop`, the routine a check's timeout uses (`killpg` on POSIX, `taskkill /T /F` on Windows), so an MCP server or a shell it started does not outlive the call. `tests/test_claude_code.py` holds a stand-in that starts a child which starts a grandchild, each writing a heartbeat, and checks that both stop after `provider_timeout`; it runs on whichever platform the suite runs on (CI runs it on Linux and Windows). The lookups a failed or timed-out call's stream showed are journaled before the failure is raised (below).

## The query guard

GitHits' privacy line is that it sees only the agents' queries, never code, and that every lookup is in the factory's record. The record half was #80 (`lookup` facts with a digest of each query). The guard is the other half: a query that carries a secret, an email, a private URL or a block of the repository's code is stopped on this machine, before Claude Code sends it.

**The hook.** `syberlabs/query_guard.py` is a Claude Code `PreToolUse` hook. For every call the provider creates a temporary directory of its own (outside the worktree and the repository), writes there the guard's policy (`policy.json`), the digests of the worktree's lines (`tree_lines.txt`) and a settings document (`settings.json`) that holds exactly this:

```json
{"hooks": {"PreToolUse": [{"matcher": "^(mcp__githits__.*|WebSearch|WebFetch)$", "hooks": [{
  "type": "command", "command": "<the host's python>", "args": ["-I", "<host checkout>/syberlabs/query_guard.py", "<guard directory>"],
  "timeout": 30, "onFailure": "block"}]}]}}
```

and passes it with `--settings`. The script is the host's own file by absolute path, as a critic program is (`docs/CRITIC.md`), so a candidate cannot rewrite its guard; `-I` keeps the worktree's directory and `PYTHONPATH` off the import path, so the worktree's own `syberlabs` is never imported. The hook loads only the two standard-library modules it needs from beside itself, `canonical.py` and `_patterns.py`, by path, and not the `syberlabs` package, whose `__init__` imports the whole SDK. The three files are written read-only and the directory is removed after the call.

**What keeps the record the hook's.** The guard's directory is a plain directory of the operator's user outside the worktree, so three things stop a model from forging a `pass` or weakening the guard there:

1. *Exact matching.* A decision counts for a lookup only when its `tool_use_id` equals the stream's `tool_use` id and its tool and query digest equal the lookup's. There is no fallback match by tool and digest. A hook input with no `tool_use_id` is blocked (`guard_error`) before the lookup leaves, and its decision matches nothing, so the lookup reads `unguarded` and the search stops.
2. *A MAC under a key no file holds.* For each call the host draws a random 256-bit key (`secrets.token_hex(32)`) and puts it, with the SHA-256 of `policy.json` and `tree_lines.txt`, into Claude Code's environment (`SYBERLABS_GUARD_KEY`, `SYBERLABS_GUARD_POLICY_DIGEST`, `SYBERLABS_GUARD_TREE_DIGEST`). The hooks reference documents no per-hook `env` field; it says "A hook process inherits the parent environment", so that is how the hook gets them. The hook writes each decision with `mac`, HMAC-SHA256 over the canonical JSON of `{tool_use_id, tool, query_digest, rule}`; the host keeps only decisions whose MAC verifies (`query_guard.authentic`). A missing or wrong MAC is `unguarded`. A hook started without the key blocks (`guard_error`).
3. *A checked, read-only policy.* `policy.json` (and `tree_lines.txt`) are written read-only; the hook compares each file's SHA-256 with the digest in its environment and blocks (`guard_error`) when they differ, instead of obeying a rewritten threshold or an emptied tree list. The policy's digest is on every candidate as `signal.guard.policy_digest`.

What can read the key: the Claude Code process, the hook, and every other process Claude Code starts with its environment, which includes stdio MCP servers (the GitHits server process) and code-running tools: every child of Claude Code inherits it, not the hook alone. So the MAC shows that a decision was written by a process holding the key. It protects against a model that has only the file tools forging or altering a decision (it can neither read the environment nor reach the guard's directory) and against a decision file left by anything outside the run; it does not show that the hook wrote the decision, because the GitHits server, or any other child of Claude Code, could sign one. The model reaches the environment only through a code-running tool (`Bash`, `PowerShell` and the like). None is in the default `--allowed-tools`, and under `--restricted` none exists unless `--tools` names it, which the provider does only for a tool the operator allows by name; **allowing `Bash` or another code-running tool weakens this**: a shell can read the key and sign a forged decision, and can change files outside the working directories, the host's own `query_guard.py` among them. **So when `--mcp-config` names any MCP server, or `--githits` is on, the provider refuses a code-running tool** in `--allowed-tools` when it is built (`invalid_provider`, with the reason): `Bash` and `PowerShell`, the two `--restricted`'s help names (`claude_code.CODE_TOOLS`, compared ignoring case, `Bash(git log *)` counted as `Bash`). The one exception is the `Bash(<launcher>:*)` entry the provider itself adds for each `--githits` call; an operator's own `Bash(...)` entry, a `Bash(<some path>:*)` included, is still refused. An `--mcp-config` file that is not a JSON object whose `mcpServers` is absent or empty counts as naming a server. `--allow-code-tools-with-mcp` overrides; it is recorded on every candidate as `signal.guard.allow_code_tools_with_mcp: true`. A code-running built-in the help does not name is not refused (`spec/GAPS.md` 57). The digest check of `policy.json` and `tree_lines.txt` still holds against a shell alone, because a child process cannot change the environment of the Claude Code process that starts each hook. The file tools cannot reach the guard's directory: `--restricted` "confines the file tools to the working directories", and under `dontAsk` a call that would need approval is denied (both above). With `CLAUDE_CODE_SUBPROCESS_ENV_SCRUB=1` Claude Code may strip a variable whose name looks like a credential from the hook's environment (the env-vars page); the hook then has no key and blocks every lookup (`guard_error`), which fails closed.

**The contract it relies on**, read from Anthropic's hooks reference (`code.claude.com/docs/en/hooks`, 2026-10-23) and the installed `claude --help` (2.1.309): a `PreToolUse` hook receives `tool_name`, `tool_input` and `tool_use_id` (with the common `session_id`, `cwd`, `hook_event_name` fields) as JSON on standard input; exit code 2 blocks the tool call and Claude Code hands the hook's standard error to the model as the denial reason; exit 0 lets the call go ahead, and the model never sees a passing hook's standard error; any other exit code is a non-blocking error unless `onFailure: "block"` is set (Claude Code 2.1.295 and later), which also blocks on a timeout or a hook that cannot start. A matcher with characters other than letters, digits, `_`, `-`, `,`, `|` and spaces is an unanchored JavaScript regular expression, hence the anchors; `mcp__githits__.*` matches every GitHits tool. `args` makes the hook exec form (no shell), which matters on Windows, where a shell-form hook runs in Git Bash or PowerShell.

**The rules.** Each outbound text is judged on its own: every string of the tool input, dictionary keys included, for every matched tool (`WebFetch`'s `prompt` too: it is processed off this machine, not by the site, but it still leaves it). Each text is judged as typed and again folded (`query_guard.fold`: Unicode NFKC, so fullwidth and other compatibility forms read as their plain letters; every format character, category `Cf`, removed, such as a zero-width space or joiner, a direction mark or a soft hyphen; and the Cyrillic and Greek letters that look like Latin ones mapped to them), and a rule broken by either form blocks. The first rule broken wins:

| Rule | Blocks |
|---|---|
| `secret` | A credential shape: the pattern set `syberlabs.metrics` refuses in a note, one object defined in `syberlabs/_patterns.py` (`ghp_`, `gho_`, `ghs_`, `github_pat_`, `sk-ant-`, `sk-`, `xox?-`, `AKIA`, followed by 8 or more key characters; the guard requires a word start, so `risk-assessment` is not an `sk-` key), a PEM private-key header, or a bearer token. |
| `url_credentials` | A URL with a user name or password before the host (`scheme://user:pass@host`). |
| `email` | An email address. |
| `too_long` | More than `max_chars` characters (default 400). |
| `code_fence` | A fenced block (three backticks or three tildes). |
| `code_lines` | More than `max_lines` non-blank lines (default 3). |
| `tree_line` | A line that, whitespace-normalized and at least 16 characters long, occurs verbatim in a tracked file of the worktree the call started from. The host hashes every such line of the parent's tracked files (SHA-256, 32 hex characters kept) before the run; the hook compares digests and never holds the tree's text. |
| `guard_error` | The hook could not read its input or its policy. A guard that cannot judge blocks. |

An allowed query passes unchanged and silently (exit 0, no output). A blocked one gets one line on standard error naming the rule and asking for a short question about a public package; it never repeats the query. Every decision is written beside the hook as `{tool_use_id, tool, query_digest, rule}`: no query text.

**What is recorded.** The provider reads those decisions after the run and keeps a decision for a lookup only when its MAC verifies and its tool use id, tool and query digest are the lookup's (above). A blocked lookup is still a lookup: its `lookup` record has `ok: false` and `guard: "<rule>"`; an allowed one `guard: "pass"`. The thresholds are recorded on every candidate as `signal.guard: {version, max_lines, max_chars, policy_digest}` (`version` is `2` since the hardening). A lookup with no verified decision is recorded `guard: "unguarded"`, and the call fails `provider_guard_inactive`: the search stops with that error and no further call is made, because the guard did not run (a Claude Code that skipped the hook, a managed policy that allows only managed hooks, `disableAllHooks`, a server-side tool the hook cannot see) or its record is not the hook's, and the operator must find out before the next lookup, not after a pilot. A call that ends `provider_failed` or `provider_timeout` journals every lookup its stream showed, with its `guard` (`unguarded` included), before the failure is raised: those lookups may have left the machine.

**What the operator tunes.** `--guard-max-lines N` and `--guard-max-chars M` on `syberlabs propose --claude-code`, or `SYBERLABS_GUARD_MAX_LINES` and `SYBERLABS_GUARD_MAX_CHARS` in the host's environment (the flags win), or `guard_max_lines` and `guard_max_chars` on `ClaudeCodeProvider`. They are host policy, never contract data. The rules themselves and the 16-character tree-line floor are fixed in `query_guard.py` (`VERSION` 1).

**Limits, stated plainly.** The guard is a filter over what the model typed, not a proof that no code leaves the machine. A model can paraphrase code, split it into several short queries, split one credential across two lookups (each half alone is no credential shape), separate a key's characters with spaces, encode it (base64, base32, hex, URL or percent-encoding, HTML entities, ROT13, Morse, one character per word: none is decoded), use a lookalike the fold does not map (only NFKC, `Cf` removal and a fixed table of Cyrillic and Greek letters are applied; Armenian, Cherokee or other scripts are not), put it inside one line of a longer query (the tree rule compares whole lines), or quote a line it wrote during the run (the digests are taken from the parent's tracked files before the run). The identifier rule the packet sketched (a path or identifier from the tree that is in no public dependency name) is not built. A false positive costs a rephrased query: a query that happens to equal a 16-character line of the tree, an `user@host` that is not an address, a long but public question. Whether Claude Code 2.1.309 runs a `--settings` hook under `--bare` is not settled by what was read: the headless page says bare mode skips the *auto-discovery* of hooks and lists `--settings` as the way to pass settings, while the installed `--help` says bare mode skips "hooks (those defined in settings and by installed plugins)". No real Claude Code ran in this packet. The fail-closed rule above is what makes either answer safe: if the hook does not run, the first lookup stops the search and the record says `unguarded`. The first live run of either lane must check that its lookups read `pass` or a rule.

## GitHits through the launcher (`--githits`, arm B)

GitHits asked for the pilot to use its API rather than its MCP server, so that the host controls and measures every lookup. `ClaudeCodeProvider(..., githits=True)` (`syberlabs propose --claude-code --githits [--githits-arm NAME]`) gives the agent exactly one way to reach GitHits, the host's own client (`syberlabs/githits.py`, `docs/GITHITS.md`), and gives arm A nothing:

```bash
syberlabs propose --claude-code --bare                 # arm A: no GitHits, and no GitHits variable
syberlabs propose --claude-code --bare --githits       # arm B: the same, plus the launcher and the skill
```

**The launcher.** For each call the provider writes, in the call's guard directory (outside the worktree, removed after the call), a read-only POSIX shell script named `githits` (`claude_code.write_launcher`):

```sh
#!/bin/sh
exec '<host python>' -I '<host checkout>/syberlabs/githits_cli_entry.py' "$@"
```

`githits_cli_entry.py` puts the host checkout first on `sys.path`, refuses to run if `syberlabs` came from anywhere else, and runs the host's GitHits client with the arguments. It accepts only the five lookups (`search`, `example`, `read`, `list`, `grep`); `doctor` and anything else exit 2 with a usage message and write no record, and `example` takes no `--license-mode`, so it always sends `license_mode: strict` (`docs/GITHITS.md`, the launcher's entry). `doctor` stays the operator's: `syberlabs githits doctor`. `-I` keeps the worktree's directory and `PYTHONPATH` off the import path, so the candidate's own `syberlabs/` never runs. Claude Code's Bash tool runs bash (Git Bash on Windows), which runs the script. The launcher is named by its absolute path with forward slashes, the exact text the model types; a path holding a space or a quote is refused (`provider_unavailable`).

**What arm B adds.** Argv: `Bash` in `--tools`, `Bash(<launcher>:*)` in `--allowedTools`, and the skill after the harness note in `--append-system-prompt`. Environment, for the launcher's client:

| Variable | Value |
|---|---|
| `SYBERLABS_GUARD_LAUNCHER` | the launcher's path, for the query guard |
| `SYBERLABS_GITHITS_RECORD_DIR` | `githits-records/` in the call's guard directory |
| `SYBERLABS_GITHITS_RECORD_KEY` | a fresh `secrets.token_hex(32)` per call, in no file |
| `GITHITS_SESSION_ID` | `<thread>-<arm>` (`X-GitHits-Session-ID`; GitHits allows only `[A-Za-z0-9_-]`, so not `/`) |
| `GITHITS_AGENT` | `syberfactory/<arm>` (`X-GitHits-Agent`) |
| `SYBERLABS_GITHITS_LICENSES` | the license allow list in force, written out (the operator's, else the permissive default) |
| `SYBERLABS_GITHITS_EXCLUDE` | the exclusion list in force, written out (`syberlabs` plus what the operator added) |

`GITHITS_API_TOKEN` is the operator's own, inherited from the environment and never written; the provider refuses `--githits` without it. `SYBERLABS_GITHITS_EXCLUDE_REPLACE` is never passed: an operator's switch is removed from Claude Code's environment, and the exclusion list above is computed without it, so it always begins with `syberlabs` (tested in both arms). The arm defaults to `b`. Arm B passes the operator's other GitHits variables through unchanged, as before.

**Arm A holds no GitHits variable.** Without `--githits`, and without `--mcp-config` (no GitHits route at all), the provider removes every `GITHITS_*` and `SYBERLABS_GITHITS_*` variable from Claude Code's environment (`claude_code.githits_variable`, compared ignoring case), `GITHITS_API_TOKEN` and `GITHITS_API_URL` included. Least privilege was chosen over a byte-identical environment: arm A has no tool that could use the token, and now it does not hold it either. Arm A's argv is still byte-identical to what it was before this route existed. `tests/test_claude_code.py` pins arm A's argv literally and its environment as the caller's minus those variables plus the guard's three, and pins arm B's differences to exactly the items above plus the operator's GitHits variables that arm A no longer receives. An `--mcp-config` run keeps them, because a GitHits MCP server, a child of Claude Code, may read its token from that environment (the MCP A/B below).

**The guard over Bash.** With the launcher, the query guard's matcher is `^(mcp__githits__.*|WebSearch|WebFetch|Bash)$`, and a `Bash` call passes only when its command is the launcher's exact path, alone or followed by a space, and what follows is plain words and single- or double-quoted strings (`query_guard.bash_arguments`). `not_launcher` blocks any other command; `shell_syntax` blocks a control operator, redirection, expansion or substitution anywhere (`` ; & | < > $ ` \ ( ) { } ! ``, any control character such as a newline), a glob, tilde or comment character outside quotes, an unterminated quote, and `run_in_background`. The arguments that pass are the outbound text: each one, and all of them joined, are judged by the same rules as a GitHits tool's query (`secret`, `url_credentials`, `email`, `too_long`, `code_fence`, `code_lines`, `tree_line`). Decisions carry the same MAC under the per-call key. Claude Code's own permission check is a second gate: under `dontAsk` a Bash command that `Bash(<launcher>:*)` does not name is denied.

**PowerShell under the override.** An operator's `Bash` or `PowerShell` entry is refused with `--githits` unless `--allow-code-tools-with-mcp` is passed. With the override, the matcher is `^(mcp__githits__.*|WebSearch|WebFetch|Bash|PowerShell)$` (`query_guard.MATCHER_SHELLS`), and a `PowerShell` call is judged by the same launcher-only rule as `Bash` (`query_guard.SHELL_TOOLS`): any command but the launcher is `not_launcher`, so an allowed PowerShell no longer runs unguarded. Its refusals are journaled like a refused Bash call (tool `PowerShell`, its rule) and counted in `signal.githits.bash_refused` and `lookups_blocked`. Without the override the matcher is the Bash one above.

**What is recorded.** After the call the provider reads the client's records (`githits.read_records` under the call's record key). Each authentic record becomes one verified `lookup` fact, tool `githits.<op>`, value `{tool, query_digest, request_id, status, at, results_returned, results_dropped, results_dropped_license, latency_ms, contamination_blocked, ok, guard}`: the client's own digest of the request it sent, never text. Forged or altered record lines are counted (`signal.githits.records_ignored`) and ignored. Every `Bash` call the guard did not pass is journaled as a `lookup` with tool `Bash` and its rule (or `unguarded`), which `lookups_blocked` counts. `signal.tool_usage.githits` is the number of authentic records (plus any `mcp__githits__*` call the stream shows). The candidate also carries `signal.githits: {arm, launcher_calls, launcher_passed, records, records_ignored, bash_refused, license_policy[, mismatch]}` and `signal.harness.skill: {path, sha256}`. `githits_lookups` never counts a `githits.doctor` fact.

A record cannot be tied to the tool use that ran it, so the host reconciles counts: authentic records against launcher calls the guard passed. Fewer records is `mismatch: githits_unrecorded` (a usage error, a client that failed before recording, a denied permission; recorded, the call stands). More records than guarded calls is `githits_unexpected_records`: each record of the call is journaled `guard: unguarded`, and the search stops `provider_guard_inactive`, because something holding the key ran the client without the guard.

**The skill.** `skills/githits/SKILL.md` adapts GitHits' shipped skills (`githits-com/githits-cli` at `0bc9f5e68b`, `skills/githits-code/SKILL.md` and `skills/githits-mcp/SKILL.md`, Apache-2.0, Copyright 2025 GitHits Inc.; `skills/githits/LICENSE` is the upstream license and `skills/githits/NOTICE` says what changed) for the launcher: when a lookup is worth it (an API or version fact the repository and the standard library do not settle), how to phrase a query (short, naming the package and version, no code or repository text), targets first, search then grep or list then read, results as untrusted data, and citing sources in the final reply (the harness does not commit). Claude Code 2.1.309's `--help` offers `--append-system-prompt`, `--plugin-dir` (skills inside a plugin) and `--add-dir`; the provider uses `--append-system-prompt`, so the text is part of arm B's system prompt on every request rather than a skill the model may or may not load, and arm A's prompt is exactly the harness note. The YAML front matter is left out, and `{launcher}` is replaced by the call's launcher path, so arm B's exact appended text is the harness note, a blank line, and the file's body with that one substitution; the file's SHA-256 is on `signal.harness.skill`, computed with CRLF normalized to LF, so a Windows checkout with `core.autocrlf` records the committed blob's digest (`24c150e4…6508` today) as a POSIX one does. `.gitattributes` (`skills/** text eol=lf`) also checks the skill out with LF on every platform.

**Not verified here.** No real Claude Code and no real GitHits ran. The tests use a stand-in `claude` whose Bash tool is emulated (a command no `Bash(<prefix>:*)` rule names is denied; the launcher's `exec` line is run as `sh` would run it) and a loopback fake GitHits; a separate test runs the launcher under a real `sh` when one is on `PATH`. Whether Claude Code 2.1.309 matches `Bash(<absolute path>:*)` against a Windows path with forward slashes, and runs it through Git Bash, is for the first live call: `syberlabs githits doctor`, then one guarded lookup whose record and fact are checked.

## GitHits A/B through MCP

Before `--githits`, the pilot's route was an MCP server. With this provider the only difference between those arms is `--mcp-config FILE`:

```bash
syberlabs propose --claude-code --bare --allowed-tools Read,Edit,Write,Glob,Grep,WebSearch,WebFetch,mcp__githits   # off
syberlabs propose --claude-code --bare --allowed-tools Read,Edit,Write,Glob,Grep,WebSearch,WebFetch,mcp__githits \
    --mcp-config githits.json                                                                                       # on
```

Use the same `--allowed-tools` in both arms; the off arm has no GitHits server to call (`--strict-mcp-config` is always passed), so naming its tools there changes nothing. The two argv vectors differ in the last two items only, apart from the path of each call's own temporary guard settings file; the guard and its policy are the same in both arms (`tests/test_claude_code.py` pins this). The `init` event's MCP servers and their status are recorded in `signal.harness.mcp_servers`, so a reader can see that GitHits connected in the on arm.

## What is recorded, and what is not

Per call, on the candidate's `signal` (all parsed by the host from the stream, bounded, and never taken from the model's text):

- `model_usage`: input, output and cache-read and cache-creation tokens summed over the run's assistant messages, counted once per message id (Claude Code repeats a message's usage on every content block it streams), with `model` when one model served the run; `model_usage_by_model` when more than one did;
- `harness_turns`: the result's `num_turns`; `harness_stop`: the result's `subtype`;
- `tool_usage`: `{web_search, web_fetch, githits, other: {tool: n}}`. GitHits is any `mcp__githits__*` tool; web is `WebSearch`, `WebFetch` and the server tools `web_search` and `web_fetch`. It is bounded by `providers.tool_usage`: at most 16 other names;
- `harness`: Claude Code's version, model, effort, the credential source name (`apiKeySource`, never a credential) and the MCP servers with their status;
- `lane`, `cost_basis`, `estimated_usd`, and `skipped_paths` (how many changed files were binary, not UTF-8 or over 1 MiB, and so left out);
- `guard`: the query guard's policy for the call, `{version, max_lines, max_chars}`;
- with `--githits`: `githits` (launcher calls, records, mismatch; above) and `harness.skill`.

Per lookup (each GitHits or web tool call), one verified `observed` event, key `lookup`, source and actor `syberlabs.host`, version `<search>.<call>.<n>`, value `{tool, query_digest, query_chars, at, ok, guard}`. The provider writes it through the search space (`SearchSpace.observe`; `GitSearchSpace.observe` records it with `Session.observe` and accepts only the key `lookup`, a value of at most 4096 bytes and a short version), so a provider built in Python keeps its lookups in the journal; there is no callback from the CLI any more. `query_digest` is the SHA-256 of the query string: `query` for WebSearch and GitHits search, `url` for WebFetch, otherwise the tool input as canonical JSON. `at` is when the host read the line (the stream carries no time of its own). `ok` is false when the stream holds no successful result for that call, or the guard blocked it. `guard` is `pass`, a rule name or `unguarded` (the query guard, above). A call's lookups are recorded before its candidate.

**Not recorded anywhere in the journal:** the prompt, the query text, tool inputs and results, the model's text and Claude Code's session id. A reader can count and date lookups and tell whether two runs searched for the same thing; they cannot read what was searched. A call that changed nothing is refused `no_change` with its usage, but without its lane, turns or tool counts (`spec/GAPS.md` 54).
