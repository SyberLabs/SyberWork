# Economic actions in SyberWork

An economic action is an external effect proposed by a human or model, admitted by Barn, claimed durably, and executed by an administrator installed settlement adapter. The first implementation supports `purchase_capability` and `transfer`; reserving budget is an internal part of committing either action. Release occurs only for an adapter guaranteed no-write rejection. Refund and conditional settlement need separate destination contracts.

The installed `economic_http` action fixes its HTTPS endpoint, same-origin status lookup, operation (`purchase_capability` or `transfer`), rail, asset, counterparty and credential environment variable. Loopback test adapters may omit the credential. It is a trusted settlement-service interface, not an x402 client or a wallet. The adapter MUST deduplicate by `Idempotency-Key`, persist an authoritative status record, and return a matching receipt. No model supplied URL or wallet key is accepted. An adapter assertion is not independent on-chain verification.

The global policy supplies `economic`: `budget_id`, `budget_units`, `max_amount_units`, `asset`, `rail`, and `counterparties`. The immutable contract supplies nonempty verified `required_facts`, an `amount_units` binding to one of those verified facts, and optionally a stricter `max_amount_units` and independent `approval_role`. Each proposal supplies exactly `operation`, `amount_units` (canonical positive integer string, e.g. USDC atomic units), `asset`, `counterparty`, `purpose`, `evidence` (the latest observation event hashes for every required fact), and `expires_at` (Unix seconds no more than one hour from evaluation). The case ID is the workflow reference. The policy budget ID identifies a shared budget across cases. A policy revision can lower but cannot increase an existing budget ID's cap or change its asset; use a distinct ID for a new allocation.

For example, the administrator publishes an action with `kind: "economic_http"`, `operation: "purchase_capability"`, `asset: "USDC:base"`, `counterparty: "vendor-A"`, `rail: "usdc_service"`, an HTTPS `url`, a same-origin `status_url` ending in `/{key}`, and `auth_env: "PAYMENT_SERVICE_TOKEN"`. A policy may set `budget_id: "research-q3"`, `budget_units: "1500000"`, `max_amount_units: "1000000"`, and `counterparties: ["vendor-A"]`. The contract must bind `amount_units` to a verified quote such as `fact:quote.units`. The actor proposes with that exact amount, the recorded quote event hash in `evidence`, a purpose, and a near expiry. An independent manager approves when the contract or policy requires one.

Admission checks the configured operation, rail, asset and counterparty, exact unit limits, all source freshness/provenance checks, evidence event hashes, expiry, and the aggregate budget. Commit rechecks under a SQLite write lock, persists an `effect_started` event containing hashes of the policy, evidence and intent plus a reservation in the same transaction, then invokes the adapter. A successful receipt must match state `settled`, key, canonical request digest, amount, asset, counterparty, and nonempty external ID. A malformed response or transport failure is **unknown**, retaining its reservation. A configured prewrite rejection (409/412/428) releases it. Destination status reconciliation can settle an unknown or interrupted started outcome; 404 is inconclusive. An unresolved claim blocks another attempt of that action. The adapter is responsible for its own transaction finality and custody controls.

The receipt and proposal are present in the case hash chain, but the database owner can alter that chain. The system does not sign events, verify chain finality, hold funds, discover x402 offers, or grant unlimited spending. Configure a real adapter only after validating its idempotency and status contract against the provider. Existing non-economic actions retain their present behavior.
